# Advanced Testing

*Group 2 - Part 1*

You already know the four generic tests. This topic is about testing things generic tests can't express: relationships between columns *within* a row, and invariants that only show up when you compare a model's row count to its own upstream source. Both exercises live in `mediapulse_base`.

## Exercise

Singular tests are just a `.sql` file in `tests/` that should return zero rows when everything is healthy. You'll write one against a real computed column.

### Step 1 - Read the target column

- [ ] Step complete

Open `mediapulse_base/models/marts/ads/fct_ad_impressions.sql`. Look at how `click_through_rate` is calculated, including the `case` branch for `impressions_count = 0`.

---

### Step 2 - Decide the invariant

- [ ] Step complete

Write down, in plain English, what should always be true about `click_through_rate` for every row - not just "it exists," but a relationship between it and the columns it's derived from.

---

### Step 3 - Write the singular test

- [ ] Step complete

Create a `.sql` file in `tests/` that selects the rows where your invariant is violated. Remember: a singular test *passes* when it returns zero rows.

??? tip "Hint: What a singular test is"
      A singular test is a stored query, not a special test type - dbt just runs it and fails the build if it returns rows. See [Add data tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) for the exact mechanics and where singular test files live.

---

### Step 4 - Run it against real data

- [ ] Step complete

Build `fct_ad_impressions` and run just your new test. If it fails, work out whether the data is wrong or your invariant was.

??? tip "Hint: Selecting a single test"
      You can target one test by name with `dbt test --select`. The [test selection examples](https://docs.getdbt.com/reference/node-selection/test-selection-examples) page shows the syntax for selecting individual tests versus whole test suites.

---

**Deliverable:** the singular test file, plus one sentence stating the invariant it enforces and why a generic test couldn't express it.

## Extension

`fct_streaming_events`'s own YAML description already admits something uncomfortable: *"Subscriptions are joined on user_id without a date-range filter."* You're going to look into the consequences of this with a test.

### Step 1 - Find the fan-out with a row-count test

- [ ] Step complete

Write a singular test comparing the row count of `fct_streaming_events` to the row count of the staging model it's built from (the watch-events staging model in `mediapulse_base`'s streaming domain). A one-to-many enrichment join like this should not change the row count - if it does, something upstream is duplicating rows per event.

??? tip "Hint: Comparing counts across two relations in one test"
      You need a query that references two different `ref()`s and compares aggregates between them - a single `select ... from a, b` style test, not a per-column generic test. This is exactly the "compare a model to its own source" pattern discussed in [Add data tests to your DAG](https://docs.getdbt.com/docs/build/data-tests).

---

### Step 2 - Confirm the cause, not just the symptom

- [ ] Step complete

Using what the model's YAML already tells you, explain in your own words *why* the join produces extra rows for some users and not others. Which users are unaffected?

---

### Step 3 - Reason about the fix's shape - don't write it

- [ ] Step complete

Without changing the model, describe what condition the join to `dim_subscriptions` would need in order to pick exactly one subscription per event (for example, something that relates `watched_at` to a subscription's active window). What new problem would that introduce if a user has gaps between subscriptions, or two subscriptions that overlap?

---

### Step 4 - Decide where this test should live long-term

- [ ] Step complete

Would you keep this as a permanent singular test guarding `fct_streaming_events`, or is it a one-off diagnostic you'd delete once the model is fixed? Justify your answer.

---

**Deliverable:** the singular test proving the fan-out and a corrected model using a data comparison in the join statement.
