## Coding

Catalog is for finding problems so fixing them still means opening the project. `dim_subscriptions` has a naming problem worth fixing for real.

### Step 1 - Question the grain

- [ ] Step complete

The first column looks like the primary key - `user_id` - but there is no unique test. 

Add a `unique` test to `user_id` on `dim_subscriptions` (alongside its existing `not_null` test) and run it. Before you run it, predict: given what `dim_subscriptions` actually models, is `user_id` a safe column to expect uniqueness on?

### Step 2 - Rename it to match what it actually is

- [ ] Step complete

`dim_subscriptions` isn't a slowly-changing dimension - it's one row per subscription event. Rename the model file to `fct_subscriptions_accumulating_snapshot.sql`, rename its `subscription_id` column to `subscription_event_id` (since that's what's actually unique per row), and update its YAML entry to match. Confirm with a search across the project that nothing else `ref()`s the old name before you rename it.

??? tip "Hint: fct_/dim_ naming conventions"
      dbt's own [how we structure marts](https://docs.getdbt.com/best-practices/how-we-structure/4-marts) guidance explains the distinction this exercise is about - a `dim_` name implies stable, one-row-per-entity attributes, not events.

### Step 3 - Build `dim_active_subscribers`

- [ ] Step complete

Create a new mart, `dim_active_subscribers`, with one row per subscriber currently on an active plan. Decide for yourself whether a subscriber could end up with more than one "currently active" row in this data, and if so, how your model should handle it so the result is genuinely one row per subscriber.

??? tip "Option: A ready-made dedup model does exist for this"
      There's an existing intermediate model that already deduplicates subscriber records. You can either build on top of this (easier) or decide the dedup logic yourself (harder). 

**Deliverable:** the renamed `fct_subscriptions_accumulating_snapshot` model and YAML, and the new `dim_active_subscribers` model with a test proving its grain is genuinely one row per subscriber.
