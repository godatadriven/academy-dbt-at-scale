# dbt Catalog & Review

*Group 2 - Part 1*

You've likely seen dbt Catalog (formerly dbt Explorer) before, so treat this as a fast checkpoint rather than a first look - then push straight into the part that's new to you: seeing a dbt Mesh boundary through Catalog's eyes.

## Exercise

**Prerequisite:** a production (or staging) deployment environment for `mediapulse_platform`, with at least one successful `dbt build` job run.

**Goal:** confirm you can still navigate Catalog confidently, quickly.

1. **Birds'-eye view**
   Open Catalog for `mediapulse_platform`. Using the sidebar resource counts, answer: how many marts does this project have, and which domain (ads, news, podcasts, streaming) has the most?

2. **Lineage check**
   Find `dim_campaigns` and trace its full upstream lineage back to a source. How many hops does it take?

3. **Recommendations sweep**
   Open the **Recommendations** tab and list every distinct type of recommendation currently raised (not just one). Which type shows up most often?

   ??? tip "Hint: Recommendations mirror dbt_project_evaluator"
       If a recommendation type is unfamiliar, the [dbt Catalog FAQs](https://docs.getdbt.com/docs/explore/dbt-explorer-faqs) page explains where recommendations come from and how they map onto the open-source `dbt_project_evaluator` rules.

**Deliverable:** a one-line summary per step - this is a review, keep it tight.

## Extension

This is your first real look at dbt Mesh in action. `mediapulse_analytics` depends on `mediapulse_platform` for several of its staging models, and Catalog can show you that relationship directly - and help you diagnose a real bug that spans the boundary.

**Context:** `fct_content_performance.sql` in `mediapulse_analytics` is marked *"work in progress - review the join logic before using downstream."* It joins `stg_news__articles` to `stg_podcasts__episodes` **on `category`** - a many-to-many join key - producing a row-count fan-out.

1. **Multi-project view**
   Open Catalog's account-level lineage and confirm `mediapulse_platform` appears as an upstream project to `mediapulse_analytics`.

   ??? tip "Hint: Cross-project lineage is Enterprise/Enterprise+"
       Cross-project relationships appear as dashed lines between project nodes; a project's **Relationships** tab lists downstream projects that reference it. See [Explore multiple projects](https://docs.getdbt.com/docs/explore/explore-multiple-projects).

2. **Ref-able public models**
   Identify which `mediapulse_platform` staging models `mediapulse_analytics` is allowed to `ref()` across the boundary. Cross-check your answer against the `access:` config in `mediapulse_platform/dbt_project.yml` and the dependency declared in `mediapulse_analytics/dependencies.yml`.

3. **Trace the bug across the boundary**
   Open `fct_content_performance` and expand its lineage graph. Trace `stg_news__articles.category` and `stg_podcasts__episodes.category` back to their sources across the project boundary, and explain why joining on `category` alone produces the fan-out.

   ??? question "What would a correct fix change?"
       Think about what the join key should include instead - a proper unique identifier plus category, or a different strategy (e.g. stacking the two datasets rather than joining them) entirely.

**Deliverable:** a short write-up of the bug and your proposed fix direction, using Catalog's lineage view as your evidence.
