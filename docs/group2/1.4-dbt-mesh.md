# dbt Mesh

*Group 2 - Part 1*

`mediapulse_analytics` doesn't own a staging layer for news, podcasts, or ads - it reaches into `mediapulse_platform` for that data using dbt Mesh, dbt's mechanism for referencing models across project boundaries. This section is about understanding exactly what that connection allows and how it's enforced.

## Exercise

1. **Read the dependency declaration**
   Open `mediapulse_analytics/dependencies.yml`. This is what tells dbt that `mediapulse_analytics` depends on `mediapulse_platform` as a *project*, not a package. Note what's different about a project dependency compared to the `dbt_utils` package dependency declared in `packages.yml`.

   ??? tip "Hint: Package vs. project dependencies"
       A package dependency pulls in another project's full source code to compile alongside your own. A project dependency instead references a set of *public* models as an API - you never parse, compile, or run the upstream project's code yourself. See [Project dependencies](https://docs.getdbt.com/docs/mesh/govern/project-dependencies).

2. **Map the access levels**
   Open `mediapulse_platform/dbt_project.yml`. For each of these models, decide - based on its layer and any model-level overrides - whether `mediapulse_analytics` is currently *allowed* to `ref()` it: `stg_news__articles`, `stg_ads__campaigns`, `int_campaign_content_spend_allocation`, `dim_campaigns`, `dim_content_catalog`.

   ??? tip "Hint: The three access levels"
       Models default to `protected` (referenceable only within their own project). Only `public` models can be referenced from another project. Check both the project-level defaults and any folder-specific overrides. See [Model access](https://docs.getdbt.com/docs/mesh/govern/model-access).

3. **Verify against what's actually referenced**
   Open `mediapulse_analytics/models/marts/content/fct_content_performance.sql` and `mediapulse_analytics/models/marts/revenue/fct_ad_revenue.sql`. Find every `ref()` call that points at `mediapulse_platform`. Does the set of models actually referenced match the "public" list you built in step 2?

   ??? tip "Hint: Cross-project ref syntax"
       A cross-project reference takes the upstream project name as its first argument, e.g. `ref('mediapulse_platform', 'model_name')` - a different shape from the single-argument `ref()` you've used so far. See the syntax example in [Project dependencies](https://docs.getdbt.com/docs/mesh/govern/project-dependencies).

4. **Explain the gap**
   `dim_campaigns` and `dim_content_catalog` are both models `mediapulse_analytics` could plausibly want, and one of them is `public`. Neither is currently referenced anywhere in `mediapulse_analytics`. Why might that be - is this a missed opportunity, a deliberate scoping decision, or just a model nobody's needed yet?

**Deliverable:** A short table listing all five models from step 2 with their access level, whether `mediapulse_analytics` is allowed to reference them, and whether it actually does.

## Extension

If you finish early, go a level deeper into how the mesh connection actually behaves at build time - this is where the mental model of "it's just like `ref()`" starts to break down.

1. **Figure out what "public" really depends on**
   A model being `access: public` isn't the only requirement for cross-project `ref()` to resolve. Research what else has to be true upstream (in `mediapulse_platform`) before `mediapulse_analytics` can successfully reference one of its public models in a real deployment.

   ??? tip "Hint: It's not just the access config"
       Cross-project references resolve against the upstream project's most recent successful deployment, not its raw code. Read the "producer" prerequisites in [Project dependencies](https://docs.getdbt.com/docs/mesh/govern/project-dependencies).

2. **Trace the consequence of a live edit**
   Suppose someone edits `stg_ads__campaigns.sql` in `mediapulse_platform` right now and saves it. Based on what you found in step 1, would `mediapulse_analytics`'s next `dbt build` pick up that change immediately? Under what conditions would it, and under what conditions would it silently keep using the old version?

3. **Break it on purpose (on paper)**
   `fct_ad_revenue.sql` references `stg_ads__campaigns` and `stg_ads__spend` from `mediapulse_platform` using the two-argument `ref()`. If `mediapulse_platform` changed either model's `access` from `public` to `protected`, what specifically would happen the next time `mediapulse_analytics` tried to parse or run - would it fail silently, fail loudly, or something else?

   ??? tip "Hint: What access violations actually produce"
       Referencing a model your access level doesn't permit raises a specific, named error at parse/run time - it's not a silent no-op. See the access enforcement notes in [Model access](https://docs.getdbt.com/docs/mesh/govern/model-access).

**Deliverable:** A short written explanation of exactly what mechanism - not just "it depends on access" - determines whether a change in `mediapulse_platform` is visible to `mediapulse_analytics` at any given moment.
