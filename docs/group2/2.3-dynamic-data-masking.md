# Dynamic Data Masking

*Group 2 - Part 2*

Dynamic data masking is a **Snowflake** feature, not a dbt one - dbt's job is to help you apply and manage masking policies as part of your deployment pipeline, not to mask data itself. Knowing where that line sits is the real skill here.

## Exercise

`stg_news__authors` (and the `dim_authors` mart built on top of it) carries a genuine `email` column all the way through - a realistic candidate for masking.

1. **Understand the feature, not the syntax**
   Read up on Snowflake's Dynamic Data Masking. What is a masking policy attached to (a column, a table, a schema)? What decides whether a given query sees the real value or a masked one?

   ??? tip "Hint: Where masking policies live"
       A masking policy is a schema-level object in Snowflake - it has to be created in a database/schema before it can be attached to a column. See [Understanding Dynamic Data Masking](https://docs.snowflake.com/en/user-guide/security-column-ddm-intro).

2. **Design a policy for `email`**
   In prose, describe what a masking policy on `stg_news__authors.email` (or `dim_authors.email`) should do. Which role(s) should see the real address? What should everyone else see - fully redacted, partially masked (e.g. `j***@newsnow.com`), or something else?

   ??? question "Whose decision is this?"
       This is a data governance call, not a technical one - dbt and Snowflake will happily implement whatever rule you give them. Who in a real organisation would own this decision?

3. **Work out where the policy gets applied**
   dbt doesn't have a native "masking" feature. Two real options exist: the `grants` resource-config, or a `post-hook`. Which one is actually meant for this job?

   ??? tip "Hint: grants vs. post-hook"
       dbt's [`grants` config](https://docs.getdbt.com/reference/resource-configs/grants) manages standard object privileges (`select`, `insert`, etc.) - it does not cover masking policies. The [`post-hook`](https://docs.getdbt.com/docs/build/hooks-operations) docs are explicit that hooks are for things you *can't* do with `grants`, which is exactly where masking policies fall. That's your answer, but explain *why* in your own words.

4. **Decide where in the project this belongs**
   Would you write one `post-hook` per model that has a sensitive column, or something more centralised (e.g. a macro applied via `dbt_project.yml` config to every model matching a naming/tag convention)? What are the tradeoffs?

   ??? tip "Hint: A real starting point"
       You don't have to invent this from scratch - `dbt-snow-mask` is an existing community package built specifically for tagging columns and applying Snowflake masking policies from within a dbt project. Skim its approach for ideas, even if you don't install it: [dbt-snow-mask on GitHub](https://github.com/entechlog/dbt-snow-mask).

**Deliverable:** A short written design: which column gets masked, the masking rule, which role(s) are exempt, and whether you'd implement it via `post-hook` directly or via a package/macro pattern - with your reasoning.

## Extension

Data doesn't stay in one place. `email` starts in `stg_news__authors` (a view) and flows into `dim_authors` (a table) - and conceptually could be exposed further downstream still.

1. **Trace the masking requirement through the layers**
   Snowflake masking policies attach to a physical column on a physical table or view. Since `stg_news__authors` and `dim_authors` are two separate physical objects (dbt rebuilds `dim_authors` as its own table), does applying a masking policy once "upstream" protect the column everywhere it's copied to, or does the policy need to be reapplied at every materialized layer that carries the column?

   ??? tip "Hint: Objects, not lineage"
       Masking policies protect a *column on a specific database object* - Snowflake has no concept of "this data came from a masked source, so mask it here too." Confirm this by re-reading how policies are set on [table and view columns](https://docs.snowflake.com/en/user-guide/security-column-ddm-use), and think through what that means for `dim_authors` specifically.

2. **Design for the real project structure**
   Given your answer to step 1, propose a rule for this project: should every model that carries `email` (`stg_news__authors`, `dim_authors`, and any future model) reapply the policy independently, or is there a way to make this consistent without repeating yourself in every model file? (You've seen macros elsewhere in this workshop - is there a natural fit here?)

3. **Consider the failure mode**
   What happens to your masking guarantee if someone adds a new mart that selects `email` from `dim_authors` and forgets to apply the policy to the new physical table? Is there a way to catch this in CI, or is this fundamentally a code-review/process problem rather than a tooling one? Be honest about the limits of automation here.

**Deliverable:** A short write-up of your propagation rule (reapply-per-model vs. a shared macro/convention), plus one concrete idea for catching a missed masking policy before it reaches production.
