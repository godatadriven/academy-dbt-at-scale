# Jinja/Macros & Custom Schema Logic

*Group 2 - Part 1*

A deeper look at one specific, real macro in this project: `mediapulse_platform`'s custom `generate_schema_name` override, and what it means that this override doesn't automatically apply to `mediapulse_analytics` too.

## Exercise

**Goal:** understand exactly why this override exists, and check whether the newer analytics-side seeds actually need one.

1. **Read the macro in full**
   Open `mediapulse_platform/macros/generate_schema_name.sql`. Identify the two branches: one for seeds under `_seeds_setup`, one for everything else.

??? tip "Hint: The two behaviors"
      For `_seeds_setup` seeds, a custom schema name is used exactly as given (no prefix). For everything else, dbt's normal `{{ target_schema }}_{{ custom_schema_name }}` pattern applies. See [Custom schemas](https://docs.getdbt.com/docs/build/custom-schemas) for how `generate_schema_name` is invoked and what context it has access to.

2. **Explain the "why"**
   Why does `mediapulse_platform` need seed schemas to land *exactly* as configured (e.g. `news`, `podcasts`, `ads`, `streamview_legacy`) rather than getting a target-schema prefix? What would go wrong for the project's `source()` definitions if seeds landed in a prefixed schema instead?

3. **Predict where the analytics seeds actually land**
   Open `mediapulse_analytics/seeds/_seeds_setup/_seeds_setup.yml` (the CRM seeds) and `mediapulse_analytics/models/staging/crm/_crm__sources.yml`. `mediapulse_analytics` has no `generate_schema_name` override of its own yet. Using dbt's *default* macro behavior (no override), work out which schema each CRM seed will actually land in, and compare that to the schema its `source()` definition expects. Do they match?

4. **Fix it**
   Create `mediapulse_analytics/macros/generate_schema_name.sql` (the `macros/` folder doesn't exist yet in this project - you'll be creating it). Check `mediapulse_analytics/seeds/_seeds_setup/` first: decide whether `mediapulse_platform`'s exact branching logic is the right fix for `mediapulse_analytics`, or whether something different is needed, then implement whichever you conclude is correct.

5. **Check the seed that isn't under `_seeds_setup`**
   `mediapulse_analytics/seeds/map_streaming_legacy_fields.csv` sits directly in `seeds/`, with no schema override configured anywhere for it. Confirm whether your new macro changes where this seed lands, and explain why or why not.

**Deliverable:** your answer to step 2, the new macro file, and your written answers to steps 3 and 5.

## Extension

dbt Mesh doesn't share macros across projects the way it shares public models. Reason through what that actually means in practice.

1. **The constraint**
   `generate_schema_name` is a project-level override - each dbt project gets exactly one, and it is not inherited from an upstream project through a `dependencies.yml` relationship.

??? tip "Hint: Macro dispatch and packages"
      If you want to genuinely share macro logic across projects (not just override behavior locally), the relevant dbt concepts are packages and [macro dispatch](https://docs.getdbt.com/reference/dbt-jinja-functions/dispatch) - not dbt Mesh's model-level `ref()`/`access` system, which only governs models.

2. **Duplicate a different macro for real**
   The cents-to-dollars pattern (`contract_value_cents / 100.0`) shows up in `mediapulse_analytics/models/marts/crm/fct_advertiser_contracts.sql`. Write a small macro under `mediapulse_analytics/macros/` that takes a column name and returns the cents-to-dollars expression, and edit `fct_advertiser_contracts.sql` to call it instead of the inline division. You now have a second, independently-written macro doing a similar job to whatever `mediapulse_platform` might have for the same pattern - a real instance of the duplicate-vs-share tension, not a hypothetical one.

3. **Work through the scenario**
   Given the macro you just wrote, and the `generate_schema_name` override you wrote in the Exercise: for each one, would you rather (a) leave it duplicated per-project, (b) extract it into a small internal package both projects install via `packages.yml`, or (c) something else? Argue for one option per macro - they don't have to get the same answer.

4. **Generalize the lesson**
   Beyond schema naming, name one other kind of project-level configuration (hint: think about what else lives in `dbt_project.yml` alongside `models:` and is not covered by `access:`) that a dbt Mesh setup does *not* automatically share between projects, and explain why that matters for teams maintaining multiple mesh projects.

**Deliverable:** the new macro file, the edited `fct_advertiser_contracts.sql`, your recommendation from step 3 with reasoning, and your answer to step 4.
