### Step 4 - Document the intermediate model

You may have already noticed, but the `int_shows_clean_string_columns` model is not currently documented outside of the comments in the file. 

Use the `dbt Wizard` to add this documentation to the `_int__models.yml` file.

??? hint "Hint: How to pass in a good prompt"
      The dbt Wizard will look at your whole project to determine how it needs to edit or add things. 
      Be precise by telling the Wizard which file it needs to look into, and which commands it should and shouldn't run. 
      For example, the following prompt:

            Add documentation to the yaml file for this model.

      can be vastly improved:

            Update the file `_my_yaml_file.yml` to add documentation for currently selected model, using the existing inline SQL comments.

            Please do the following:

            1. Follow the same structure, indentation, and 
            style already used for other models in this yaml file (don't reformat 
            or reorder existing entries).

            2. Write a `description` for the model that explains its purpose. 
            Base this description on the logic and comments already present in 
            the model's SQL file — don't invent behavior that isn't in the code.

            3. Document each output column with a `description`, inferring column 
            purpose from the SQL. Note in the description when a column 
            has been transformed/cleaned vs. passed through unchanged.

            4. Add appropriate column-level tests where they make sense given 
            existing conventions in this file (e.g. `not_null` and `unique` on 
            the primary key column) — only add tests that match patterns 
            already used elsewhere in the yaml file, don't introduce new 
            testing conventions.

            5. Do not modify any other model's documentation, tests, or 
            formatting in this file — only add the new entry.

            Show me the diff before applying it so I can review the added YAML 
            block.

## Extension

### Step 1 - Refactor SQL logic for best practice

- [ ] Step complete

dbt projects tend to accumulate logic in the wrong layer over time — a 
transformation that started in a staging model gets copy-pasted into three 
downstream models instead of being centralized, or business logic ends up 
living in a mart when it really belongs further upstream. This step is 
about spotting the drift and correcting for it.

Look at the `podcasts` source and everything built on top of it. Trace 
the logic across staging, intermediate, and mart models and ask:

- Is the same transformation (a calculation, a filter, a case statement) 
  repeated in more than one place instead of being defined once?
- Is any model doing work that conceptually belongs in an earlier or 
  later layer — e.g. cleaning logic sitting in a mart, or aggregation 
  logic sitting in staging?

Review everything dependent of the `podcasts` source and refactor any code that belongs in a different model. 

??? tip "Hint: where to start"
      Not sure where to begin? Use the dbt Wizard to run a review on 
      everything dependent on the `podcasts` source. This will cover `staging`, 
      `intermediate`, and `mart` models built downstream of it. Ask it to 
      identify any logic that seems out of place for its layer, and to 
      flag redundant or repetitive code (the same transformation defined 
      more than once across different models).

??? tip "Hint: what to look out for"
      A few specific things worth checking as you review:

      - Does the `staging` model convert `datetime` columns from strings to 
        actual timestamp types, or is that left for later (or never 
        done at all)?
      - Are any `sources` being joined together at the 
        `staging` level? Joins like this usually belong in an 
        `intermediate` or `mart` model, not `staging`.
      - Is a `seed` being used anywhere in `staging`? This isn't necessarily 
        a problem on its own, but it's worth discussing whether it's 
        the right pattern.

### Step 2 - Give an orphaned intermediate model a consumer

You job in this step is to build one. Make sure:

- The model is saved in the right location
- The appropriate materialization is applied
- Is well documented with yaml configuration
- Is appropriately named according to the project design and best practice
- Has good test coverage

??? tip "Hint: naming and layering"
      Give the mart a name that reads as a summary, not a pass-through (dbt's [model naming conventions guide](https://docs.getdbt.com/best-practices/how-we-structure/4-marts) has examples of mart-layer naming). Since you're grouping and aggregating, this belongs in `marts/`, not another intermediate model.
