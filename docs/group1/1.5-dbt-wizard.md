# dbt Wizard

*Group 1 - Part 1*

dbt Wizard is dbt's AI assistant inside the Studio IDE - it has access to your project's structure, lineage, and metadata, not just a blank chat window. Used well, it's a fast way to generate boilerplate (YAML, tests, docs) and investigate unfamiliar code. Used badly, it's a fast way to ship something wrong with confidence. This section is about learning the difference, on real `mediapulse_base` work.

## Exercise

### Step 1 - Ask it to explain, before asking it to change anything

- [ ] Step complete

Open `mediapulse_base/models/intermediate/int_campaign_content_spend_allocation.sql` in Studio IDE and ask dbt Wizard to explain what the model does and why the allocation rule branches by `campaign_type`. Compare its explanation against the model's own YAML description in `_int__models.yml` - does it match, add anything useful, or get anything subtly wrong?

??? tip "Hint: reference specific models directly"
      Type `@` inside the dbt Wizard panel to reference a specific model by name and scope its context to that file, rather than asking a vague question about "the project." See [dbt Wizard in Studio IDE](https://docs.getdbt.com/docs/dbt-ai/wizard-ide) for how model references and quick-actions work.

---

### Step 2 - Use it for real, low-risk boilerplate

- [ ] Step complete

Pick one of the columns you left undocumented back in the Testing exercise (in `mediapulse_base/models/staging/ads/_ads__models.yml`) and ask dbt Wizard to generate a description and suggest an appropriate generic test for it, using dbt Wizard's quick-action for tests/docs rather than free-form chat.

---

### Step 3 - Review the diff, then actually apply it

- [ ] Step complete

Before accepting anything dbt Wizard proposes, look at the diff it shows you. Is the generated description actually accurate for this column, or is it a plausible-sounding guess? Is the suggested test one you'd have chosen yourself in the earlier Testing exercise? Edit the proposal if it's wrong, then apply it so `_ads__models.yml` is genuinely updated on disk - this isn't a thought experiment, the file should be different by the end of this step.

??? tip "Hint: it shows you a diff, not a fait accompli"
      dbt Wizard proposes file changes as a diff for you to review before they're persisted - the default mode requires your approval before it applies anything. See [dbt Wizard in Studio IDE](https://docs.getdbt.com/docs/dbt-ai/wizard-ide) for the approval-vs-auto-apply modes.

---

### Step 4 - Ask it something it genuinely can't verify

- [ ] Step complete

Ask dbt Wizard whether `int_campaign_content_spend_allocation` is currently referenced by any mart. Then check for yourself by searching the project. Did it get this right, and how confident should you be in an AI assistant's claims about your project's actual state versus its explanation of code it can directly read?

---

**Deliverable:** one thing dbt Wizard got usefully right, one thing it got wrong or overstated, and the description/test you ended up keeping (yours, its, or a merge of both) with your reasoning.

## Extension

### Step 1 - Give it a harder, multi-file task, then commit to a real file

- [ ] Step complete

Ask dbt Wizard to draft a new small mart that summarizes total `allocated_spend_cents` per `campaign_type` from `int_campaign_content_spend_allocation` (the same orphaned-model opportunity from the Modeling refresh topic). Let it propose the model file and, separately, ask it to propose the YAML documentation for it. Fix anything wrong or missing in its draft yourself, then save both files for real under `mediapulse_base/models/marts/ads/` and build the model.

---

### Step 2 - Stress-test its project awareness

- [ ] Step complete

Ask it to also propose a `relationships` test tying your new mart back to `stg_ads__campaigns`. Does it correctly identify that this new mart and `stg_ads__campaigns` are both in `mediapulse_base` (same-project reference), or does it show any confusion about project boundaries if you mention `mediapulse_analytics` in the same conversation?

---

### Step 3 - Decide where you'd actually use it going forward

- [ ] Step complete

Based on everything you've seen today, write a short, honest policy for yourself: which categories of work in this project would you delegate to dbt Wizard by default (e.g. YAML scaffolding), which would you always hand-write, and which would you accept its first draft but always independently re-verify (e.g. claims about lineage or "is this tested")?

??? question "What's actually being reviewed here?"
      dbt Labs' own guidance is to review proposed changes as diffs before they're persisted - but a diff review only catches whether the *code* looks reasonable, not whether an explanation or claim about your project's state is *true*. Which of today's exercises exposed that gap most clearly?

---

**Deliverable:** your new mart and its YAML (accepted, rejected, or edited from dbt Wizard's draft, your call), the outcome of the relationships-test project-boundary check, and your written policy for when you would and wouldn't lean on dbt Wizard.

!!! success "Done?"
      You've used dbt Wizard for real boilerplate and a real multi-file build, and you've written down where you trust it and where you don't. That judgement matters more than the tool itself.
