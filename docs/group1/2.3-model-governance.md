# Model Governance

*Group 1 - Part 2*

`mediapulse_platform` already uses one governance feature without you having touched it: every model in the project has an `access` modifier, set in `dbt_project.yml`. This section is about understanding what's already there, then extending it deliberately.

## Exercise

1. **Read the current access configuration**
   Open `mediapulse_platform/dbt_project.yml`. Note the `access` setting for each layer: staging is `public`, intermediate is `protected`, and marts are `protected` by default except the `streaming` marts folder, which is overridden to `public`.

   ??? tip "Hint: what each access level means"
       `public` models can be referenced from anywhere, including other dbt Mesh projects; `protected` (the default) can only be referenced within the same project; `private` restricts referencing to models in the same `group`. See [Model access](https://docs.getdbt.com/docs/mesh/govern/model-access) for the full behaviour of each level.

2. **Explain the current choices**
   Why do you think staging models are `public` here, given `mediapulse_analytics` needs to `ref()` several of them? Why are the `ads` and `podcasts` marts left `protected` while `streaming` marts are `public` - what does that tell you about which marts are meant to be consumed outside this project?

3. **Introduce a model group**
   Pick a small cluster of related models (e.g. the `ads` staging + marts models) and assign them to a `group` in `dbt_project.yml`. Set one model's access to `private` and confirm (by trying to reference it from outside the group) that dbt enforces the restriction.

   ??? tip "Hint: groups and private access"
       A `group` gives a set of models a named owner, and `private` access restricts a model so only other models in the *same* group can reference it - useful for models that are genuinely internal implementation details, not stable interfaces. See [About model governance](https://docs.getdbt.com/docs/mesh/govern/about-model-governance) for how groups and access levels combine.

**Deliverable:** your explanation of the current access choices, plus your new group definition and a screenshot/log showing the `private` restriction being enforced (or the compile error it produces).

## Extension

1. **Design a model contract**
   Pick one mart that's already relied upon downstream - `dim_campaigns` is a strong candidate, since it's documented as a shared dimension both `mediapulse_platform` and `mediapulse_analytics` are meant to join to. Work out what a `contract: enforced: true` config would require you to specify for it, and what would happen if you changed a column's data type without updating the contract.

   ??? tip "Hint: what a contract actually checks"
       An enforced contract validates a model's returned column names, order, and data types against what's declared in its YAML *before* the model is allowed to build - it fails fast rather than letting a silent schema drift reach consumers. See [Model contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts) for exactly what's validated and what constraints you can add on top.

2. **Decide whether this change needs a model version**
   Suppose you needed to rename a column on a contracted, `public` model that other teams already depend on. Research what dbt model versions are for, and explain why "just changing the column name" is the wrong move once a model has consumers outside your control.

   ??? tip "Hint: versions exist for breaking changes"
       Model versions let multiple versions of a model coexist (e.g. `dim_campaigns_v1`, `dim_campaigns_v2`), with a `latest_version` marking the default and a `defined_in` config pointing each version at its file - giving consumers a migration window instead of forcing an immediate break. See [Model versions](https://docs.getdbt.com/docs/mesh/govern/model-versions) for the exact config shape.

3. **Write the governance plan, not the implementation**
   Produce a short written plan: which models in `mediapulse_platform` deserve a contract given who consumes them, and under what circumstance you'd reach for a model version instead of just editing the model in place.

**Deliverable:** your contract design for the mart you chose, and your written governance plan.
