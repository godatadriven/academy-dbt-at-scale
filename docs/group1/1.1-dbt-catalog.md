# dbt Catalog

*Group 1 - Part 1*

Before touching any code today, get comfortable navigating dbt Catalog (formerly dbt Explorer) - it's how you'll orient yourself in a project you didn't build, and how you'll debug problems by tracing lineage instead of guessing from SQL alone.

## Exercise

**Prerequisite:** a production (or staging) deployment environment for `mediapulse_platform`, with at least one successful `dbt build` job run, so Catalog has metadata to display.

**Goal:** use Catalog to understand a multi-source, multi-layer project's health and lineage before touching any code.

1. **Birds'-eye view**
   Open Catalog for `mediapulse_platform`. Using the sidebar resource counts (Model / Source / Test / Seed, etc.), answer:
   - How many sources vs source tables does this project have?
   - Are there any sources with zero downstream models?

2. **Advanced search**
   Use the filter panel to filter by **Modeling layer = Staging**. Find `stg_news__articles` and open it.

3. **Column-level lineage**
   On `stg_news__articles`, click into the `category` column and trace it downstream. Where does `category` ultimately end up? Does it get renamed or transformed anywhere along the way?

   ??? tip "Hint: Column-level lineage is an Enterprise feature"
       If you don't see per-column lineage, check your plan tier - column-level lineage is only available on Enterprise and Enterprise+ plans. See the [dbt Catalog FAQs](https://docs.getdbt.com/docs/explore/dbt-explorer-faqs) for the full feature-by-plan breakdown.

4. **Project recommendations**
   Open the **Recommendations** tab. Pick one "Missing Primary Key Test" (or similar) recommendation and identify which resource it's flagging, and whether it's a real gap or a false positive given how the model is structured.

   ??? tip "Hint: Where recommendations come from"
       Catalog's recommendations largely mirror the checks in the open-source `dbt_project_evaluator` package, so the same reasoning you'd apply to that package's output applies here. See the [dbt Catalog FAQs](https://docs.getdbt.com/docs/explore/dbt-explorer-faqs).

5. **Deliverable**
   A short written note: *"If I were about to build the streaming staging layer, what does Catalog tell me I should watch out for, based on test/doc coverage elsewhere in this project?"*

## Extension

`mediapulse_platform` isn't the whole story - `mediapulse_analytics` is a second dbt project connected to it through a dbt Mesh dependency. Catalog can show you that relationship, and it's the fastest way to diagnose a bug that spans a project boundary without ever opening the SQL.

**Context:** `fct_content_performance.sql` in `mediapulse_analytics` is marked *"work in progress - review the join logic before using downstream."* It joins `stg_news__articles` to `stg_podcasts__episodes` **on `category`** - a many-to-many join key, not a proper join condition - which will produce a row-count fan-out.

1. **Multi-project view**
   Open Catalog's account-level lineage and confirm `mediapulse_platform` appears as an upstream project to `mediapulse_analytics`, with its public models visible as nodes.

   ??? tip "Hint: Where to look"
       Cross-project relationships show up as dashed lines between project nodes, and a project's **Relationships** tab lists which downstream projects reference it. See [Explore multiple projects](https://docs.getdbt.com/docs/explore/explore-multiple-projects). This view is Enterprise/Enterprise+ only.

2. **Ref-able public models**
   Identify which `mediapulse_platform` staging models `mediapulse_analytics` is allowed to `ref()` across the project boundary, and cross-check that against `mediapulse_analytics/dependencies.yml` and the `access:` settings in `mediapulse_platform/dbt_project.yml`.

3. **Multi-project lineage**
   Open `fct_content_performance` in `mediapulse_analytics` and expand its lineage graph. Trace both `stg_news__articles.category` and `stg_podcasts__episodes.category` back to their sources across the project boundary.

   ??? question "Why not column-level, here?"
       Cross-project lineage in Catalog currently stops at the model level - it won't trace a specific column's history once it crosses a project boundary. Keep that limitation in mind as you reason about the bug below.

4. **Diagnose using lineage, not SQL**
   Using only what the lineage view and model descriptions show you (not the SQL file), explain *why* joining on `category` alone causes a row-count blowup, and propose what the join key *should* include instead.

5. **Deliverable**
   A one-paragraph write-up of the bug, using Catalog's lineage view as your evidence rather than the SQL file.
