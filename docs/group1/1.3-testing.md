# Testing

*Group 1 - Part 1*

`mediapulse_platform` is not fully tested on purpose - it sits at roughly 50% column-level test coverage, so there are real gaps for you to find and reason about, not just a checklist to complete. This section is about deciding *which* columns actually deserve a test, and using a test failure as a diagnostic tool rather than something to silence.

## Exercise

1. **Find the gaps**
   Open `mediapulse_platform/models/staging/ads/_ads__models.yml`. For each of `stg_ads__campaigns`, `stg_ads__impressions`, and `stg_ads__spend`, list which columns currently have no `data_tests` at all.

2. **Decide what's actually worth testing**
   Not every untested column is a real gap. For each column you listed in step 1, decide: does it need a test, and if so, which one (`not_null`, `unique`, `accepted_values`, `relationships`)? Some columns (like a free-text `campaign_name`) may genuinely not need one.

   ??? tip "Hint: the four generic tests"
       dbt ships four built-in generic tests - `unique`, `not_null`, `accepted_values`, and `relationships` - and they cover most quality checks you'll need here. See [Add tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) for what each one checks and how to configure them under a column's `data_tests:` key.

3. **Add the tests you decided on**
   Update `_ads__models.yml` with the tests from step 2. Run them selectively before running the whole project.

   ??? tip "Hint: selective test runs"
       You don't need to run the whole project to check your work. `dbt test` (or `dbt build`) accepts a `--select` flag with a model name, so you can target just the models you changed. See [Node selection syntax](https://docs.getdbt.com/reference/node-selection/syntax) for the selection methods available.

4. **Read the model, not just the YAML**
   Open `mediapulse_platform/models/staging/ads/stg_ads__campaigns.sql`. Notice it selects directly from `mediapulse_raw.ads.campaigns` rather than using a `source()` reference. What does that cost you, in terms of what dbt can test and document about the raw table itself?

**Deliverable:** your updated `_ads__models.yml`, plus a one-line justification for each test you added (and, for any column you deliberately left untested, why).

## Extension

Not every bug shows up as a missing test - sometimes the test is already half-right, and it's telling you something you haven't noticed yet.

1. **Look for the hidden bug, test-first**
   Open `mediapulse_platform/models/staging/news/_news__models.yml`. `article_id` already has a `not_null` test, but not a `unique` test. Add `unique` to `article_id` and run it.

   ??? tip "Hint: read the failure, don't just react to it"
       A failing test in dbt returns the *offending rows*, not just a pass/fail flag - the compiled test is itself a `select` you can run directly to inspect what failed. See [Add tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) for how generic test failures surface their result set.

2. **Diagnose, don't fix**
   Query `mediapulse_raw.news.articles` directly (not the staged model) and investigate why `article_id` isn't unique there. Look at `updated_at` for the duplicated ids specifically.

   ??? question "What does the pattern tell you?"
       Is this random dirty data, or does it look like a deliberate, explainable pattern (e.g. articles being versioned over time)? That distinction changes whether the right fix is deduplication logic in staging, or a different kind of test entirely (like `dbt_utils.unique_combination_of_columns` on `article_id` + `updated_at`).

3. **Decide - don't implement - the fix**
   In prose, describe what you'd change in `stg_news__articles.sql` to make the `unique` test on `article_id` pass, and what you'd need to keep the model correct downstream (hint: which row per `article_id` is the "current" one?). Do not write the SQL - this diagnosis is the deliverable, the fix belongs to a later exercise.

**Deliverable:** a short written diagnosis of why `article_id` isn't unique, backed by what you saw querying the raw table - not just a guess from reading the SQL.
