# Jinja & Macros

*Group 1 - Part 1*

dbt models are Jinja templates under the hood. Macros let you turn repeated SQL into a reusable, named piece of logic - and `mediapulse_platform` already has one real example for you to read before writing your own.

## Exercise

**Goal:** understand a real custom macro, then spot a piece of duplicated logic that's a genuine candidate for one.

1. **Read the existing macro**
   Open `mediapulse_platform/macros/generate_schema_name.sql`. This overrides dbt's built-in macro of the same name.

   ??? tip "Hint: Why projects override this macro"
       dbt calls `generate_schema_name` to decide which schema a model or seed lands in. Projects override it when the default `{{ target_schema }}_{{ custom_schema_name }}` pattern isn't what they want. See [Custom schemas](https://docs.getdbt.com/docs/build/custom-schemas) and [Jinja and macros](https://docs.getdbt.com/docs/build/jinja-macros).

2. **Explain the branch**
   In your own words, explain what this macro does differently for seeds inside the `_seeds_setup` folder versus everything else in the project. When does a custom schema name get a `{{ target_schema }}_` prefix, and when doesn't it?

3. **Find duplicated logic**
   Compare the `budget_cents / 100.0` calculation in `dim_campaigns.sql`, the `monthly_fee_cents / 100.0` calculation in `dim_subscriptions.sql`, and the `contract_value_cents / 100.0` calculation in `mediapulse_analytics`'s `fct_advertiser_contracts.sql`. Same pattern, three separate places.

4. **Design a macro (no code required)**
   Sketch, in prose, a macro signature that would DRY up the cents-to-dollars pattern above. What parameter(s) does it need? Does it need to handle rounding, or is that the caller's job?

**Deliverable:** your explanation from step 2, plus your macro design from step 4.

## Extension

Go beyond a single-purpose macro and think about Jinja control structures and where reusable logic should actually live.

1. **Learn the control structures**
   Read up on Jinja's `{% if %}` / `{% for %}` blocks and the `{{ this }}` and `{{ target }}` variables.

   ??? tip "Hint: Where these are documented"
       See [Jinja and macros](https://docs.getdbt.com/docs/build/jinja-macros) for the full context object available inside macros, including `this`, `target`, and `var()`.

2. **Design a normalization macro**
   `mediapulse_platform`'s streaming marts documentation explicitly notes that `genre` and `device_type` have mixed casing "not normalised here." Sketch, in prose, a macro that takes a list of columns and generates a normalization expression for each - think about what it would need as inputs (column names? a mapping of raw to canonical values?) and where it would be called from.

3. **Decide where it belongs**
   Before you'd write this macro in `mediapulse_platform/macros/`, check whether `dbt_utils` (already a dependency in `packages.yml`) already ships something close to what you need.

   ??? question "Build vs. reuse"
       Search the [dbt_utils package hub page](https://hub.getdbt.com/dbt-labs/dbt_utils/latest/) for macros related to string cleanup or SQL generation. If nothing fits exactly, what would you look for in the macro's design to make it reusable enough that it doesn't need rewriting the next time a new mixed-casing column shows up?

**Deliverable:** your macro design from step 2, and a short note on whether you'd write it yourself or found something in `dbt_utils` worth adapting instead.
