# Jinja & Macros

*Group 1 - Part 1*

dbt models are Jinja templates under the hood. Macros let you turn repeated SQL into a reusable, named piece of logic - and `mediapulse_platform` already has one real example for you to read before writing your own.

## Exercise

**Goal:** understand a real custom macro, then spot a piece of duplicated logic that's a genuine candidate for one.

1. **Read the existing macro**
   Open `mediapulse_platform/macros/generate_schema_name.sql`. This overrides dbt's built-in macro of the same name.

??? tip "Hint: Why projects override this macro"
      dbt calls `generate_schema_name` to decide which schema a model or seed lands in. Projects override it when the default `{{ target_schema }}_{{ custom_schema_name }}` pattern isn't what they want. See [Custom schemas](https://docs.getdbt.com/docs/build/custom-schemas) and [Jinja and macros](https://docs.getdbt.com/docs/build/jinja-macros).

2. **Explain the branch**
   In your own words, explain what this macro does differently for seeds inside the `_seeds_setup` folder versus everything else in the project. When does a custom schema name get a `{{ target_schema }}_` prefix, and when doesn't it?

3. **Find duplicated logic**
   Compare the `budget_cents / 100.0` calculation in `mediapulse_platform/models/marts/ads/dim_campaigns.sql` and the `monthly_fee_cents / 100.0` calculation in `mediapulse_platform/models/marts/streaming/dim_subscriptions.sql`. Same pattern, two separate places in this project (the same pattern also shows up a third time in `mediapulse_analytics`, which you'll get to if you work in that project later).

4. **Write the macro and apply it**
   Create a macro under `macros/` that takes a column name and returns the cents-to-dollars expression. Then edit both `dim_campaigns.sql` and `dim_subscriptions.sql` to call your macro instead of the inline division, and confirm both models still build correctly.

??? tip "Hint: defining and calling a macro"
      A macro is defined with `{% macro %}...{% endmacro %}` and called from a model with `{{ your_macro_name(...) }}` - exactly like a built-in Jinja function. See [Jinja and macros](https://docs.getdbt.com/docs/build/jinja-macros) for the full syntax and how arguments are passed.

**Deliverable:** your explanation from step 2, plus the new macro file and the two edited models.

## Extension

Go beyond a single-purpose macro and think about Jinja control structures and where reusable logic should actually live.

1. **Learn the control structures**
   Read up on Jinja's `{% if %}` / `{% for %}` blocks and the `{{ this }}` and `{{ target }}` variables.

??? tip "Hint: Where these are documented"
      See [Jinja and macros](https://docs.getdbt.com/docs/build/jinja-macros) for the full context object available inside macros, including `this`, `target`, and `var()`.

2. **Check for reuse before you build**
   `mediapulse_platform`'s streaming marts documentation explicitly notes that `genre` (in `dim_content_catalog`) and `device_type` (in `fct_streaming_events`) have mixed casing "not normalised here." Before writing anything, check whether `dbt_utils` (already a dependency in both projects' `packages.yml`) already ships a macro close to what a trim-and-lowercase normalization would need.

??? question "Build vs. reuse"
      Search the [dbt_utils package hub page](https://hub.getdbt.com/dbt-labs/dbt_utils/latest/) for macros related to string cleanup or SQL generation. If nothing fits exactly, what would you look for in the macro's design to make it reusable enough that it doesn't need rewriting the next time a new mixed-casing column shows up?

3. **Write and apply the macro**
   Create a macro that takes a column name and returns a trimmed, lowercased version of it. Apply it to `genre` in `dim_content_catalog.sql` and to `device_type` in `fct_streaming_events.sql`, replacing the raw column references. Then update each model's YAML description to remove the "mixed casing... not normalised here" caveat, since it no longer applies.

**Deliverable:** your build-vs-reuse note from step 2, the new macro, the two edited models, and the two updated YAML descriptions.
