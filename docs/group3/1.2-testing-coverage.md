# Testing Coverage

*Group 3 - Part 1*

By this point you should be fluent in generic and singular tests. This section is less about writing your first test and more about auditing coverage *systematically* across a project you didn't build, and reasoning about where a test belongs.

## Exercise

1. **Pick a domain and audit it end to end**
   Choose either the CRM domain (`mediapulse_analytics/models/staging/crm/_crm__models.yml`) or the StreamView legacy domain (`mediapulse_analytics/models/marts/streamview_legacy/_marts__streamview_legacy__models.yml`). For every model in it, list every column that currently has zero `data_tests`.

2. **Prioritise the gaps**
   Not all gaps are equal. Rank your list from step 1: foreign keys and enum-like status columns with no `accepted_values`/`relationships` test first, purely descriptive text/notes fields last.

??? tip "Hint: what usually matters most"
      Missing primary-key tests (silent duplicates) and untested foreign keys are typically the highest-risk gaps in a project audit - they hide structural problems, not just cosmetic ones. See [Add tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) for the full generic test set you have to close these with.

3. **Close the top gaps**
   Add tests for your top-priority items from step 2. If you chose the CRM domain, check `stg_crm__touchpoints.rep_id` and `stg_crm__contracts.start_date`/`end_date` specifically - read the model first to confirm what a reasonable test actually is.

4. **Justify what you left untested**
   For at least two columns you deliberately did not test, write one sentence each on why.

**Deliverable:** your prioritised gap list, the tests you added, and your untested-column justifications.

## Extension

1. **Add a same-project relationships test that's currently missing**
   Find a real, currently-untested foreign key relationship *within* `mediapulse_analytics` (not crossing into `mediapulse_platform`) and add a `relationships` test for it.

??? tip "Hint: relationships test structure"
      `relationships` takes a `to` (a `ref()` or `source()`) and a `field`, and fails if any value in the tested column doesn't exist in the target. See [Add tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) for the exact argument structure.

2. **Now try to do the same thing across the project boundary**
   `mediapulse_analytics` depends on `mediapulse_platform` via `dependencies.yml` and already `ref()`s several of its public staging models (e.g. `stg_ads__campaigns`, `stg_news__articles`). Before writing anything, research whether a `relationships` test can validate a foreign key against a model that lives in a *different* dbt Mesh project the same way `ref()` can cross that boundary for a model definition.

??? tip "Hint: verify this directly, don't assume"
      Cross-project references and testing don't necessarily behave identically - what's resolvable at build time via `ref()` isn't automatically the same thing as what a generic test's `to:` argument can target. Confirm the current, real answer against [Model access](https://docs.getdbt.com/docs/mesh/govern/model-access) and [Project dependencies](https://docs.getdbt.com/docs/mesh/govern/project-dependencies) rather than guessing from how `ref()` behaves.

3. **Write up the constraint and its implication**
   Explain, in your own words, what you found in step 2, and what it means for how a mesh-consuming project like `mediapulse_analytics` should validate data it doesn't own (e.g. does the validation responsibility sit with the producer project, the consumer, or both?).

**Deliverable:** your new same-project `relationships` test, and your written explanation of the cross-project testing constraint with a source link backing it up.
