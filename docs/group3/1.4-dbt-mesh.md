# dbt Mesh

*Group 3 - Part 1*

You're working across both `mediapulse_platform` and `mediapulse_analytics` from day one, so you can move through mesh fundamentals quickly and get straight to mapping how the two projects actually connect today.

## Exercise

1. **Confirm the dependency direction**
   Check both `mediapulse_analytics/dependencies.yml` and `mediapulse_platform`'s project files. Confirm the dependency is one-directional - `mediapulse_analytics` depends on `mediapulse_platform`, and not the other way round.

2. **Find every real cross-project reference**
   Search `mediapulse_analytics/models` for every `ref()` call that uses the two-argument, cross-project form (`ref('mediapulse_platform', 'model_name')`). There are a small, specific number of them, spread across exactly two models.

   ??? tip "Hint: Cross-project ref syntax"
       Cross-project references pass the upstream project's name as the first argument - a different shape from a normal single-project `ref()`. See [Project dependencies](https://docs.getdbt.com/docs/mesh/govern/project-dependencies).

3. **Check each one against access**
   For every model you found in step 2, confirm in `mediapulse_platform/dbt_project.yml` that it's actually `access: public` (or inherits public access from its folder). A cross-project `ref()` to a non-public model would fail - so if these are in the codebase and presumably building successfully, they should all check out.

4. **Draw the map**
   Produce a plain list (not code) of the full current cross-project dependency graph: which `mediapulse_analytics` model references which `mediapulse_platform` model, grouped by the `mediapulse_analytics` mart that consumes them.

**Deliverable:** Your cross-project dependency list from step 4, plus a one-sentence note on whether the current set of public models in `mediapulse_platform` is larger or smaller than what's actually being used.

## Extension

1. **Notice what ISN'T a mesh dependency**
   Open `mediapulse_analytics/models/staging/streamview_legacy/_streamview_legacy__sources.yml` and `mediapulse_analytics/models/staging/crm/_crm__sources.yml`. Both define `source()` blocks reading from a shared raw database. Neither goes through `mediapulse_platform` at all.

2. **Articulate the distinction precisely**
   Two dbt projects reading the same physical raw tables via their own independent `source()` definitions is architecturally different from one project depending on another via dbt Mesh's `ref()` mechanism - even though both involve "shared data" in some sense. Write out, precisely, what's different: what coupling exists in one case that doesn't in the other, and what happens to each project if the *other* project is deleted entirely.

   ??? tip "Hint: A source dependency is on the warehouse, not on a project"
       A `source()` reference only depends on a physical table existing in the warehouse - dbt has no concept of which (if any) other project loaded that table. A cross-project `ref()` depends on another dbt project's build/deployment lifecycle and its declared public interface. Compare how each is defined by reading [About dbt Mesh](https://docs.getdbt.com/docs/mesh/about-mesh) alongside the standard `source()` reference behavior.

3. **Apply it to a real question**
   If `mediapulse_platform`'s deployment failed entirely tomorrow (no successful production run), which parts of `mediapulse_analytics` would stop resolving, and which parts (the CRM and StreamView-legacy domains) would be completely unaffected? Justify your answer using what you now know about how each dependency type actually resolves.

**Deliverable:** A short written explanation distinguishing "two projects reading the same raw tables" from "one project depending on another via dbt Mesh," applied to the specific failure scenario in step 3.
