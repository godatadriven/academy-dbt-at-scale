# dbt Catalog & Review

*Group 3 - Part 1*

You're the most advanced track, so this page assumes Catalog fluency already and starts you straight in on dbt Mesh - it foreshadows the dedicated "dbt Mesh" topic later in this part.

## Exercise

**Prerequisite:** production (or staging) deployment environments for both `mediapulse_platform` and `mediapulse_analytics`, each with at least one successful `dbt build` job run.

**Goal:** use Catalog's cross-project features to diagnose a real bug using lineage alone - not by reading SQL first.

**Context:** `fct_content_performance.sql` in `mediapulse_analytics` is marked *"work in progress - review the join logic before using downstream."* It joins `stg_news__articles` to `stg_podcasts__episodes` **on `category`** - a many-to-many join key, not a proper join condition - producing a row-count fan-out.

1. **Multi-project view**
   Open Catalog's account-level lineage and confirm `mediapulse_platform` appears as an upstream project to `mediapulse_analytics`, with its public models visible as nodes.

   ??? tip "Hint: Where this lives"
       Cross-project relationships appear as dashed lines between project nodes; a project's **Relationships** tab lists downstream projects that reference it, and the graph reflects both direct `ref()` calls and the dependency declared in `dependencies.yml`. See [Explore multiple projects](https://docs.getdbt.com/docs/explore/explore-multiple-projects) (Enterprise/Enterprise+ only).

2. **Ref-able public models**
   Identify which `mediapulse_platform` staging/mart models `mediapulse_analytics` is allowed to `ref()` across the project boundary, using the `access:` config in `mediapulse_platform/dbt_project.yml`.

3. **Multi-project lineage**
   Open `fct_content_performance` in `mediapulse_analytics` and expand its full lineage graph. Trace both `stg_news__articles.category` and `stg_podcasts__episodes.category` back to their sources across the project boundary.

4. **Diagnose using column-level lineage**
   Explain *why* joining on `category` alone causes a row-count blowup, and propose what the join key *should* include instead - without running the model to see it fail.

**Deliverable:** a one-paragraph write-up of the bug, using only what Catalog's lineage view showed you as evidence.

## Extension

Push further than the single bug above: use Catalog to assess whether `mediapulse_platform`'s current governance setup actually supports everything `mediapulse_analytics` needs from it.

1. **A second cross-project mart**
   `mediapulse_analytics` has another cross-project-ref'd mart: `fct_ad_revenue`. Read its header comment (it flags a grain/aggregation concern of its own) and trace its lineage back through `stg_ads__spend`/`stg_ads__campaigns` in `mediapulse_platform`.

2. **Audit access against actual usage**
   Using Catalog and `mediapulse_platform/dbt_project.yml`, list every model in `mediapulse_platform` that `mediapulse_analytics` currently references or that its own documentation says it *should* be able to reference (check `dim_campaigns`'s description in particular). Are all of those models actually reachable given the current `access:` settings?

   ??? question "What would you flag to the platform team?"
       If you find a model that's documented as intended for cross-project use but isn't actually marked `public`, that's a governance gap worth writing up - not something to silently fix. This is exactly the kind of finding the "dbt Mesh" and "dbt Mesh review" topics later in this course will have you resolve properly.

3. **Recommendations at scale**
   Open Catalog's Recommendations tab for both projects and compare: does `mediapulse_analytics` (smaller, mostly self-contained CRM/legacy domains) have a meaningfully different recommendation profile than `mediapulse_platform`? What does that tell you about where technical debt tends to accumulate in a mesh setup?

**Deliverable:** a short governance audit note - which models are correctly exposed, which aren't, and what you'd raise with the platform team before building on top of them.
