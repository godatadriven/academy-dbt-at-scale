# dbt Mesh review

*Group 3 - Part 2*

This is the deepest mesh content in the workshop - an access-control audit followed by a full design exercise for extending the mesh boundary deliberately.

## Exercise

1. **Re-read the promise**
   Open `mediapulse_platform/models/marts/ads/_marts__ads__models.yml`. `dim_campaigns`'s description explicitly states it's meant to be joined by marts in *both* `mediapulse_platform` and `mediapulse_analytics`.

2. **Check whether the config backs that up**
   Open `mediapulse_platform/dbt_project.yml`. `dim_campaigns` sits in the default `marts` access tier - only the `streaming` folder is overridden to `public`. Confirm: as configured today, could `mediapulse_analytics` actually `ref('mediapulse_platform', 'dim_campaigns')` if it wanted to?

3. **Fix the mismatch**
   Decide how you'd change `dim_campaigns`'s access to match what its own documentation promises - a project-level folder override (like the `streaming` one) or a model-level `config` override just for this model. Research which is the more appropriate mechanism for a single model versus a whole folder.

   ??? tip "Hint: Where access gets configured"
       Access can be set as a project-level default per folder in `dbt_project.yml`, or overridden per model via a `config` block in that model's YAML (this moved to the `config:` key as of dbt 1.10). See [Model access](https://docs.getdbt.com/docs/mesh/govern/model-access) for both patterns.

4. **Weigh the tradeoff before you commit**
   Making `dim_campaigns` public isn't free. Write down what you'd be signing up for - what stability guarantee does a public model imply, and what would break in `mediapulse_analytics` (now or later) if `mediapulse_platform` changed `dim_campaigns`'s shape after making it public?

**Deliverable:** A recommendation - with the specific config change - for whether and how `dim_campaigns` should become public, plus the tradeoff you identified in step 4.

## Extension

The hardest task in the workshop's mesh content: design, end to end, a genuinely new cross-project connection.

1. **Define the target model**
   Design (in prose - no code) a new model that joins `mediapulse_platform`'s `dim_campaigns` with `mediapulse_analytics`'s CRM `dim_advertisers`, giving a single advertiser-level view spanning campaign spend and account/contract data. Decide which project should own this new model, and why.

2. **Work out what has to change upstream**
   Based on your fix in the main exercise, what access-level changes are now required for this new model to actually compile? Does anything in the CRM domain need to change access too, given the new model may itself need to be consumed elsewhere?

3. **Apply model governance, not just access**
   A newly-public model that other teams will build on deserves more than an access flag. Design what you'd want in place before treating it as stable: a model contract on its key columns, a decision on whether/when you'd need model versions if its shape changes later, and a group assignment reflecting who owns it.

   ??? tip "Hint: Governance is a set of tools, not one setting"
       Access, groups, contracts, and versions are four separate but related governance mechanisms - a model can have any combination of them. Review how they compose in [About model governance](https://docs.getdbt.com/docs/mesh/govern/about-model-governance).

4. **Name what you're NOT solving**
   Even with access, groups, and a contract in place, what real operational problem would still be unsolved by this design (for example: who gets notified if the upstream model's data quality changes; how CI would need to work across two projects for this one joined model)? You don't need to solve it - just name it precisely.

**Deliverable:** A short design document covering the new model's ownership, the access changes required, the governance mechanisms you'd apply and why, and the one open problem you identified in step 4.
