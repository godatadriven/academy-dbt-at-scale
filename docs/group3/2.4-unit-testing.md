# Unit Testing

*Group 3 - Part 2*

Unit tests are not the same thing as the data tests you've been writing all workshop. A data test runs against real materialized data and asks "is something wrong right now?" A unit test runs against small, hand-written mock rows and asks "does this SQL logic do what I think it does?" - before you ever touch the warehouse. dbt has supported this natively since v1.8, with a `given`/`expect` structure defined in YAML.

## Exercise

`mediapulse_platform`'s `int_episode_listen_completion` is exactly the kind of model dbt's own documentation says to unit test: it has a `case` statement with clear boundary conditions, and a capping calculation (`least(...)`) that's easy to get subtly wrong.

1. **Read the logic you're about to test**
   Open `int_episode_listen_completion.sql`. Note where `avg_completion_rate` is calculated (each session capped at 1.0 before averaging) and the four `engagement_tier` outcomes: `completed` (>= 0.75), `partial` (0.25-0.74), `dropped` (< 0.25), `no_listens` (no sessions at all).

2. **Design your mock inputs, in prose**
   Without writing any YAML yet, describe the mock rows you'd feed into the two upstream inputs (episodes and listens) to exercise each boundary:
      - a session that lands exactly on the 0.75 boundary
      - a session that lands exactly on the 0.25 boundary
      - a session whose `listen_duration_seconds` exceeds the episode's `duration_seconds` (tests the cap)
      - an episode with zero listen sessions at all (tests the `no_listens` branch, and that the left join doesn't drop the episode)

3. **Describe the expected output row for each case**
   For each mock input from step 2, write down the exact `engagement_tier` (and `avg_completion_rate`, where relevant) you expect back.

   ??? tip "Hint: given/expect structure"
       A dbt unit test defines `given` (one or more mock inputs, each tied to a real `ref()` or `source()` in the model, with rows supplied as `dict`, `csv`, or `sql`) and `expect` (the output rows your model should produce from those inputs). See [Unit tests](https://docs.getdbt.com/docs/build/unit-tests) for the full structure and where the YAML file needs to live.

4. **Place the test file correctly**
   Unlike data tests, unit test YAML doesn't belong in `tests/`. Find out (from the docs, not by guessing) where dbt expects unit test definitions to live, and why that's different from where singular tests go.

**Deliverable:** your four mock-input/expected-output pairs written out in prose, plus the correct directory for the YAML (with a one-line justification from the docs).

## Extension

Unit testing isn't limited to the platform project, and it isn't free of trade-offs - both are worth exploring.

1. **Apply it to a second model**
   Pick either `fct_advertiser_contracts`'s `contract_length_days` calculation (in `mediapulse_analytics`) or `fct_ad_impressions`'s `click_through_rate` zero-impressions branch (in `mediapulse_platform`). Design mock input/expected-output pairs the same way you did in the exercise, focused specifically on the edge case (a same-day contract, or a campaign/content pair with zero impressions).

2. **Check the constraint that matters most for this mesh**
   Before you assume you can unit test anything, anything: current dbt documentation lists specific model types and situations unit tests do *not* support - including models that live in, or are referenced from, another project. Given that `mediapulse_analytics` consumes public models from `mediapulse_platform` via the mesh dependency, work out which of your project's models a unit test genuinely cannot cover, and why that limitation exists.

   ??? tip "Hint: check the supported/unsupported list directly"
       Don't rely on memory or a summary for this - the exact list of supported and unsupported model types changes between dbt versions. Confirm against the current [Unit tests](https://docs.getdbt.com/docs/build/unit-tests) page before you commit to an answer.

3. **Decide where unit tests belong in your pipeline**
   dbt Labs has a specific recommendation about running unit tests in production versus development/CI. State that recommendation, explain the reasoning behind it in terms of what a unit test's inputs actually are, and describe how you'd configure your CI/CD pipeline (conceptually - refer back to what you built in Deployment & CI/CD) to respect it.

**Deliverable:** the second model's mock input/expected-output pairs, the specific mesh-related limitation you identified in step 2, and your CI/CD placement decision with reasoning.
