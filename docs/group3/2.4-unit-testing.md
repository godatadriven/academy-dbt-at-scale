# Unit Testing

*Group 3 - Part 2*

Unit tests are not the same thing as the data tests you've been writing all workshop. A data test runs against real materialized data and asks "is something wrong right now?" A unit test runs against small, hand-written mock rows and asks "does this SQL logic do what I think it does?" - before you ever touch the warehouse. dbt has supported this natively since v1.8, with a `given`/`expect` structure defined in YAML.

## Exercise

`mediapulse_platform`'s `int_episode_listen_completion` is exactly the kind of model dbt's own documentation says to unit test: it has a `case` statement with clear boundary conditions, and a capping calculation (`least(...)`) that's easy to get subtly wrong.

### Step 1 - Read the logic you're about to test

- [ ] Step complete

Open `int_episode_listen_completion.sql`. Note where `avg_completion_rate` is calculated (each session capped at 1.0 before averaging) and the four `engagement_tier` outcomes: `completed` (>= 0.75), `partial` (0.25-0.74), `dropped` (< 0.25), `no_listens` (no sessions at all).

---

### Step 2 - Add a `unit_tests:` block for the model

- [ ] Step complete

In `mediapulse_platform/models/intermediate/_int__models.yml`, add a top-level `unit_tests:` key (a sibling of `models:`, not nested inside it) containing at least three named unit tests against `int_episode_listen_completion`, covering:
      - a session that lands exactly on the 0.75 boundary
      - a session that lands exactly on the 0.25 boundary
      - a session whose `listen_duration_seconds` exceeds the episode's `duration_seconds` (tests the cap)

Each test needs a `given` (mock rows for the `stg_podcasts__episodes` and `stg_podcasts__listens` inputs the model actually `ref()`s) and an `expect` (the `engagement_tier` and `avg_completion_rate` you expect back).

??? tip "Hint: given/expect structure"
      Each `given` entry ties mock rows to a specific `input: ref(...)` or `input: source(...)` that the model under test actually references, with rows supplied as `dict`, `csv`, or `sql`. `expect` is the output row(s) your model should produce from those inputs. See [Unit tests](https://docs.getdbt.com/docs/build/unit-tests) for the full structure.

### Step 4 - Run your unit tests

- [ ] Step complete

??? tip "Hint: selecting only unit tests"
